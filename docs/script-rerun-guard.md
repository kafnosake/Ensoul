# 破坏性脚本的重复执行护栏与批量编辑

2026-10-11。本批处理"补丁脚本被跑第二遍导致误删"这类事故：一次批量脚本、连跑两次、删了别处的代码。

## 事故的两半

1. **脚本本身非幂等**。补丁脚本按"匹配到 X 就删/换"做事，第一次跑完锚点已经变了；第二次要么抛错（走运），要么匹配漂移到新位置，删掉本不该动的代码。
2. **写入走了没有护栏的车道**。`node x.js` 里的 `fs.writeFileSync` 绕开全部协调器：留底、语法撤回、先读后写、文件租约，一层都吃不到（见 `file-write-safety.md`："旧插件直接用 fs、终端命令、外部编辑器和其他进程不会领取租约"）。系统对"发生了什么"完全无感。

## 三条车道（改动落点）

| 车道 | 谁在用 | 走协调器？ | 护栏 |
|---|---|---|---|
| 裸 `fs` | `node x.js` 直接改源码 | 否 | 无 |
| 插件 API `api.files.write` | `patch_apply`、file-backup 回滚 | 是（`fileWrites.write`） | 租约 + 版本校验 + 原子替换 + `onFileWrite` |
| 核心工具 `write_file` / `edit` | 模型日常改代码 | 是 | 上面全部 + `onBeforeWrite` + read-guard |

结论：**把批量改写从"跑脚本"挪到"交结构化补丁"**，就一次性接回了四层保护。

## 已实现

### `plugins/patch-guard`

- `patch_apply`：一次收一组 `{ path, find, replace, expect? }`。逐条校验后**要么全改、要么一处不动** —— 有错就整批拒绝，不留半成品。写入统一走 `api.files.write`。
- **幂等**：`find` 出现 0 次且 `replace` 已在文件里 → 判为"已应用过"并跳过；出现 0 次且 `replace` 也不在 → 报"锚点漂了"，不动该文件；出现多次 → 报"不确定改哪处"，不动该文件。所以同一个补丁重发**不会**像脚本那样删到别处。
- `patch_dry_run`：同样参数，只报不写。
- **重复执行拦截**（`onBeforeTool`）：同一条命令第二次要对它上次改过的文件动手时拦下。判据不看命令里有没有危险词 —— 危险词能被 base64 绕过去，而"文件真的变了"绕不过去：
  - `onBeforeTool` 记下跑之前工作区快照；`onAfterTool` 再扫一遍，diff 出这次实际改动的文件与前后哈希（`.ensoul/state/patch-guard.json`）。
  - 它再来时，按现在的文件状态定夺：`== after` → 正是它上次留下的结果，**拦**（脚本重跑就是在这种基准上匹配）；两个都不是 → 有第三方动过，**拦**；`== before` → 文件已回到当初的输入状态，放行。
  - **看过就放行**：它上次改过的文件若随后被 `read_file` / `code_slice` 读过，放行 —— 拦的是"没看就重放"，不是"不许重跑"，和 read-guard 同一个精神。
  - **时间窗**（参数 `window`，默认 600 秒）：只对"刚跑过"的命令设防；隔久了重跑同一条命令（两次 `npm install`）不拦。
- 快照只扫源码后缀、跳过产物/缓存目录，655 个文件约 46ms。`MAX_FILES` 4000 封顶，超了不扫。
- **已知边界**：`job_start` 立刻返回，前后扫描 diff 不出内容，因此后台任务不参与记账；拦的是同步的 `run_command`，也就是事故里那一条。

### `plugins/loop-guard`

两类策略按危险程度分开：只读重复仍是"结果 + 稀疏提醒"（第 3/5/8 次）；**会动手的重复**（`run_command` / `job_start` / `run_code`）**第 2 次直接拦下**，不给跑 —— 读文件重复三次无非浪费钱，跑脚本重复两次是灾难。按面板分开计数。它拦的是"同一指纹连续出现"；隔了几步再跑由 patch-guard 按文件状态判，两者互补。

### `plugins/file-backup`

留底逻辑抽成 `keepOne`，挂到**两条钩子**上：`onBeforeWrite`（write_file / edit）与 `onFileWrite`（走协调器的插件写入，如 `patch_apply`）。只挂前者时，插件写入车道是漏的。`onFileWrite` 那条路没有"要写什么"，钩子在真正落盘前触发，于是读当前内容即旧内容。

### `plugins/tx-guard`

`WRITE_TOOLS` 白名单加入 `patch_apply`：语法校验失败当场撤回，对批量编辑同样生效。

### `AGENTS.md`

新增第 5、6 条：改源码走 `edit` / `write_file` / `patch_apply`；同一个改文件的脚本不许紧接着跑第二遍。

## 验证

- 四个插件 `node --check` 通过；行尾与仓库既有约定一致（插件 CRLF、AGENTS.md 按 .gitattributes）。
- 端到端（临时假工作区，不碰真工作区，测试脚本跑完即删）：
  - patch-guard 10 项：正常应用、幂等跳过、锚点漂移整批不动、无危险词脚本也拦、拦截持续、看过放行、回到原样放行、回退放行、只读不拦、无改动不拦。
  - loop-guard 5 项：第 2 次拦、第 3 次仍拦、换命令放行、只读第 3 次只提醒、按面板隔离。
  - file-backup 5 项：两条钩子各留底一次且存旧内容、工作区外不记、未变不留、journal 同步。
- 改动过程中 tx-guard 实际拦下一次半截修改并回滚（`file-backup` 抽函数时），说明写入守卫在本批路径上生效。

## 可靠性判断

插件层行为在隔离环境与语法门禁上把握较高。**未经真实模型端到端验收**：patch_apply 在真实批量改码场景下的通过率、拦截提示是否足以把模型引回正路、快照在超大工作区（>4000 文件）时的行为，均未验证。
