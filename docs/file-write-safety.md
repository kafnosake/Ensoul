# 文件写入协调与安全回滚

2026-10-05。本批处理多个面板同时开发时的覆盖、串事务和错误回滚，复用现有工具管线与 tx-guard。

## 已实现

- 每次实际工具调用生成独立 `toolCallId`，before/after 钩子与真实落盘事件使用同一编号；每次调用固定自己的钩子快照。
- `write_file`、`edit`、`restore_backup` 先领取文件租约，直到验证和回滚结束才释放。其他通过文件宿主写入的工具在实际写入时领取。冲突直接返回 `FILE_CONFLICT`，不让旧请求排队后偷偷覆盖新版本。
- 租约按真实路径归一化，Windows 大小写、相对路径、目录链接别名共用身份。编辑器的 `fs:write` 也不能覆盖仍在工具验证中的文件。
- `read_file` 保存面板读取的内容摘要；写入前发现内容变化就拒绝。成功写入、守卫回滚会同步更新该面板的摘要，其他面板必须重读。每面板最多保留最近 512 个路径的摘要，重启后不保留。
- 文件使用独立临时文件替换，并在提交前重新核对摘要；保留原文件权限位。守卫记录在真正写入之前落盘，记录失败则不执行写入。
- tx-guard 按调用和实际文件关联记录，保存原内容摘要与预计写入后摘要，不再从“面板 + 参数路径”猜对应事务。写后验证发现外部修改，保留当前文件；语法失败只撤回仍匹配这次写入的版本。
- 中断恢复也核对摘要。旧记录没有写后摘要时不猜测恢复；冲突移入 `.ensoul/state/tx-guard/conflicts/`，格式损坏的原记录保留。恢复失败不再宣称已经恢复。
- `restore_backup`、`rollback_recent` 接入统一写入入口，批量回滚只移除成功项的流水，未恢复项可继续调查。

冲突时读取当前文件、重新形成局部修改；不要原样重复覆盖。`WRITE_REJECTED` 表示写入未被验收接受，可能已安全撤回，也可能保留了待人工检查的恢复记录，具体看 error 与记录路径。

## 插件接入

```js
api.files.write(relativeOrAbsolutePath, text);
api.files.revision(path); // 内容摘要；不存在为 missing
api.files.restore(path, beforeTextOrNull, expectedHash);
api.onFileWrite(event => {
  // 同步、写入前；记录失败可以抛错阻止写入。
  // event: toolCallId、toolName、panelId、path、before、beforeHash、afterHash
});
```

`restore` 用于已确认版本的恢复，可以在取消收尾时运行；正常业务写入用 write，继续遵循取消信号。备份文件与插件状态不因此自动成为源码事务。守卫只验证 JSON 和能够验证的 JS 方言；TS/TSX 仍由构建验证，二进制、不可无损编码文本和超过留底上限的旧文件不做语法回滚。

## 边界

协调属于当前主进程。旧插件直接用 fs、终端命令、外部编辑器和其他进程不会领取租约；已观察到的外部版本变化会拒绝提交或回滚，但摘要检查与替换之间仍有跨进程竞争窗口，不是操作系统级 compare-and-swap。硬链接不是同一个路径身份。没有读取基线的调用也不能检查“模型此前以为是什么版本”；现有文件应先 read_file。

新 tx-guard 在旧宿主上会明确拦截相关写工具并提示退出重启，避免缺少新版桥时静默失去保护。当前仍待正常退出并重新启动应用；本批没有再次尝试被自动审批拒绝的强制重启。
